# 从零搭建一条自动内容生产流水线（案例指导教程）

> 本文以一条已经跑通的微信公众号产业研究流水线为案例，带你从零搭出属于你自己的版本。读完并照着做完，你会得到一套可运行的最小流水线：有研究底座、有结构契约、有自动门禁、有脚本化的固定动作、有 skill 调度规则、有可控交付、有数据回流。
>
> 案例账号：硬科技产业研究，个人订阅号。它的规则文件、门禁代码、生产脚本、复盘脚本都在真实稿件上迭代过多轮。本文只讲"怎么搭"，不要求你照抄它的具体规则。

**你最终要交付的东西（搭建完成的标准）**：

1. 一张填好的《平台画像卡》；
2. 一个研究包目录（含来源清单、事实台账、资料图映射）；
3. 一份结构契约（章节或卡片序列 + 每单元必须回答的问题）；
4. 一个一键执行的构建 + 门禁命令；
5. **一份脚本清单：每个固定动作对应的脚本、输入、输出、幂等与失败策略；**
6. **一张 skill 调度表：哪个阶段用哪个 skill、留什么证据、什么时候不许用；**
7. 一条可控的交付路径（只到草稿/粘贴成品，不到发布）；
8. 一套复盘台账与四路规则落盘机制。

***

## 第 0 步：开工前先做三个决定

动手写代码之前，先把这三件事定下来。定错了后面全部要返工。

### 决定一：你的内容以什么为载体

先判断，再执行对应分支：

- **如果你的内容主要靠文字承载**（读者在正文里完成阅读），走 **A 分支**。门禁重心放在"排版解析兼容性、图片托管方式、移动端不溢出"。

- **如果你的内容主要靠图片卡片承载**（读者在图片里完成阅读），走 **B 分支**。门禁重心放在"单卡字数与字号、卡序逻辑、首图信息密度、卡片比例"。

判断依据只有一个：**读者获取信息的主要位置在哪里。** 文字在正文 → A；文字在图里 → B。两者都重，按主次选一个主分支，另一个作为附加检查。

选定后不要中途切换，否则结构契约和门禁都要重写。

### 决定二：你的交付能做到哪一级

按平台实际能力选一档，写进画像卡：

- **L1 可编程草稿**：平台有草稿接口。脚本写入草稿 → 人工确认 → 人工发布。

- **L2 仅人工粘贴**：无接口但粘贴稳定。产出"粘贴友好成品" → 人工粘贴 → 人工发布。

- **L3 纯手工**：连粘贴都不稳。产出成品 + 逐项操作清单，全部人工执行。

任何一档都遵守同一条底线：**程序永远不触达"发布"这个动作。**

### 决定三：你的真实数据从哪来、多久成熟

- 只接受平台后台导出或你自己抄录的一手数据，不用第三方估算，不用接口反推。

- 确定这个平台的**数据成熟时点**（发布后多久数据才稳定到可比较）。案例用 72 小时；短周期平台可能 24—48 小时，长尾平台补 168 小时、720 小时。以你实测为准，不要照抄。

### 把三个决定填成一张卡

在项目里建 `platform_profile.yaml`（或等价配置文件），照下面填。不确定的写"待验证"，**不要凭印象填数字**：

```yaml
platform: <平台名>
carrier: text | image          # 决定一
render_target: html | markdown | image_only
render_redlines:               # 该平台编辑器已知会破坏什么，逐条列
  - <例：剥离 flex 布局 / 禁止原生列表 / 屏蔽外链图 / 不支持自定义字体>
image_policy:
  host: inline_base64 | external_url | platform_upload
  ratio_range: <平台硬限；没有就写 none>
  min_font_pt: <移动端可读下限，待验证>
structure_skeleton:            # 决定一的直接产物
  - <长文：章节条目；卡片：封面卡、内容卡、尾卡>
compliance:
  banned_terms: <该平台禁词、诱导分享词>
  identity_restrictions: <资质敏感项，如禁止证券代码、禁止导流联系方式>
delivery:
  capability: programmable_draft | manual_paste | fully_manual   # 决定二
  endpoint: <接口或人工路径>
analytics:
  snapshot_hours: <决定三>
  export_format: <xls / csv / 截图 / 接口>
  fields: <能拿到的真实字段；拿不到的一律标"资料不足">
```

**这张卡是后面所有平台相关规则的唯一来源。** 门禁代码里不允许直接写死平台规则——写死了，换平台就得改代码。

## 第 1 步：先把五条规矩写进你的规范文件

流水线跑歪，通常不是脚本写错，而是规矩没立。开工前把下面五条写进你的 `规范.md`，以后每次写稿前重读：

| 规矩     | 具体写法                                       | 违反后果                      |
| ------ | ------------------------------------------ | ------------------------- |
| 确定性边界  | 能被字符串/数值/结构/几何判定的，一律交给脚本；需要品味、权衡、担责的，一律留给人 | 让 agent 自查"是否美观"，既不通过也不失败 |
| 证据先于表达 | 先建事实台账，再写正文；自动抓到的数字先入候选池，人工核验后才允许进稿        | 把页面识别到的数字直接当事实            |
| 门禁即契约  | 每个放行条件写成：独立规则 + 唯一错误码 + 可复现检查函数 + 失败后去哪一段  | 用"完整、充分、专业"作为放行标准         |
| 人的闸门前置 | 程序终点停在可回退状态（草稿/预览），发布与定档留给人                | 脚本直接群发，出事收不回              |
| 规则增量   | 每次复盘必须产出可执行规则，落到下次会自动读取的位置                 | 复盘写完归档，下一篇照旧犯错            |

**配套两个小约束**（现在就定，不要等出事再补）：

- **资料不足配额**：允许显式标注"未找到同口径公开数据"，但设上限（案例设为全篇 2 处），并对关键模块设禁区（产业链拆解、资料图不允许不足）。

- **失败分类**：资料类失败与表达类失败必须映射成不同状态，否则修订会朝错误方向走。

## 第 2 步：搭研究底座（平台无关，先建这个）

这一步和平台无关，做完之后 A/B 两个分支都能用。

### 2.1 建目录

```
data/research/<选题>/
  source_manifest.json      # 来源清单：URL、抓取状态、快照路径、sha256
  fact_ledger.json          # 事实台账：已核验事实（初始为空）
  visual_map.json           # 资料图映射：图片、类型、模块、正文引用位置、水印状态
  module_coverage.json      # 模块覆盖：每个模块由哪些来源支撑
  core_companies.json       # 关键主体名单（产业类内容需要）
  pages/                    # 抓取快照
  images/                   # 图片候选
  research_skill_audit.json # 工具执行审计
```

### 2.2 抓取脚本只做三件事

写一个脚本，输入"选题 + 来源 URL 列表"，只做：抓取、存档、留痕。**不做任何判断。**

- 存档时保存页面快照与 `sha256`

- 自动识别到的数字写入 `collection_leads`（候选池），**不要直接写进** **`facts`**

- 图片下载后只做初筛（logo、图标、装饰图、社交按钮可直接标为 rejected）

这是防止"数字幻觉"最有效的一道结构设计：候选池与事实台账物理分离，任何数字想进正文，必须先过人工核验。

### 2.3 事实台账的八个字段

每条事实必须写全，缺一个就当门禁失败处理：

```
claim          主张（一句话）
value          数值或定性结论
period         统计期间
basis          口径 / 单位
source_id      来源编号
source_url     原始链接
verification   核验状态（verified / insufficient）
used_in_module 归属模块
```

### 2.4 研究包门禁（写完就接上）

- 可用来源数量下限（案例是 3）

- 工具执行证据必须含"实际命令 + 退出码 + 输出文件 + 哈希"——只有 `status: executed` 字样视为未执行

- 每个模块必须关联来源，或显式标注不足

- 关键模块不得标注不足

- 至少一张资料图的统计期落在时效窗口内（案例是一年）

## 第 3 步：写结构契约

结构契约不是"目录模板"，而是"**每个单元必须回答什么问题**"。门禁检查的是问题是否被回答，不是标题是否存在。

### A 分支（文字主导型）这样写

给每个章节配三样东西：标题、必须回答的问题、必须出现的字段或数值。

案例的写法可直接借鉴（章节名按你的题材改）：

| 单元       | 必须回答           | 必须出现                           |
| -------- | -------------- | ------------------------------ |
| 首屏       | 结论是什么、核心矛盾是什么  | 一张全景图/核心图，且位于结论文字之前            |
| 01 定义    | 边界在哪、包含什么不包含什么 | 至少一个可核验数值或书面边界                 |
| 02 量级    | 钱花在哪、价值量分布     | 数值 + 图                         |
| 03 拆解    | 每个子模块的构成与瓶颈    | 每子模块：功能、关键指标、缺口程度、代表主体、一张公开资料图 |
| 04 格局    | 谁在供给、集中度如何     | 数值 + 图                         |
| 05 传导    | 需求怎么变成利润       | 数值链 + 图                        |
| 06 测算    | 缺口多大、边界在哪      | 数值 + 图                         |
| 07 延伸    | 横向纵向还有什么       | 图                              |
| 08 关键主体  | 名单内每家是否被验证     | 每家：份额、壁垒、营收、利润、毛利、来源           |
| 09 来源与风险 | 证据与反证是否齐全      | 来源清单 + 风险段落                    |

### B 分支（图片主导型）这样写

同样的契约思维，单元换成卡片：

| 卡片      | 必须回答         | 硬约束               |
| ------- | ------------ | ----------------- |
| 封面卡     | 这篇讲什么、为什么值得看 | 信息密度最高，缩略图状态可读    |
| 内容卡（若干） | 每卡一个结论或一组数据  | 单卡字数上限、字号下限、一卡一主题 |
| 尾卡      | 结论与行动建议      | 不重复前面内容           |

**两种分支的共同点**：每个单元都必须有"必须回答的问题"，且必须能写成"通过/失败"。

### 结构门禁要查什么

- 单元顺序是否正确

- 必备字段是否齐全

- 每个单元是否含可核验数值，或明确写出资料边界

- 首屏图是否在结论前

- 图片是否重复

- 与上一版是否完全相同（反退化）

## 第 4 步：做呈现

### 4.1 先定图片托管方式

按画像卡里的 `image_policy.host` 决定：

- `inline_base64`：图片必须内联进成品，禁止外链（案例平台会屏蔽外链图，且外链会 404）

- `external_url`：可以用外链，但要检查链接可达

- `platform_upload`：走素材上传，成品里引用素材 ID

### 4.2 再定制图红线

写进门禁，逐条可判：

- 图片比例落在画像卡规定区间内

- 图元不超出画布

- 文字不超出画布、不超出所在容器

- 装饰图元（色条、胶囊）不压住文字

- 字号不低于画像卡下限

### 4.3 人眼放在自动检查之后

自动几何检查只能覆盖"明显越界"，判断不了真实观感。**约定固定动作：每次交付前逐张目检，记录"已逐张目检 + 张数"。** 案例曾出现脚本全过、但色条压住说明文字的漏检——这类问题只能靠眼睛发现。

### 4.4 内容与图的分工

- 数据密集型内容（多组对比、测算、成本构成、财务指标）优先做成图表，正文只留结论与拐点。

- 自制图不要做成"纯文字卡片"——图的价值在于承载数据与对比，不是把正文搬进图片。

- 引用第三方数据或结构时，图下必须标来源；保留原始水印，不裁不遮。

## 第 5 步：写五层门禁

这是整条流水线的心脏。**一条命令跑完，产出状态 + 错误码清单。**

### 5.1 分五层，按"失败意味着什么"分

| 层   | 检查什么                | 规则来源     | 失败后回到      |
| --- | ------------------- | -------- | ---------- |
| 证据层 | 来源、口径、台账、模块覆盖、时效    | 平台无关     | 第 2 步（补研究） |
| 结构层 | 单元顺序、必备字段、数值或边界     | 骨架由画像卡提供 | 第 3 步（改稿）  |
| 呈现层 | 比例、越界、超框、压字、字号、托管方式 | 全部由画像卡提供 | 第 4 步（改制图） |
| 合规层 | 禁词、承诺性表述、诱导分享、资质敏感项 | 词表由画像卡提供 | 第 3 步（改稿）  |
| 差异层 | 与上一版是否实质不同          | 平台无关     | 第 3 / 4 步  |

### 5.2 每条规则写成三要素

1. **唯一错误码**：稳定命名，能当沟通语言用，例如 `SOURCE_COUNT`、`SECTION_ORDER`、`SVG_OVERFLOW`、`BANNED_TERM`、`NO_DELTA`。
2. **定位信息**：报错必须带文件、单元、字段名。没有定位信息的报错等于没报。
3. **状态映射**：由"哪一层失败"决定回哪一步，不要统一返回"失败"。

建议的状态机（照抄即可，平台无关）：

```
RESEARCH_REQUIRED      研究不足，回第 2 步
REVISION_REQUIRED      表达/结构/呈现问题，回第 3 或第 4 步
STOPPED_NEEDS_USER     同一稿连续 3 轮失败，转人工
READY_FOR_HUMAN_REVIEW 门禁全过，等你确认
UPLOADED               已进草稿/已产出粘贴成品
PUBLISHED              你已人工发布
```

### 5.3 两个必装的特殊门禁

- **反退化门禁**：取同选题上一版成品比对，正文完全相同即失败。没有这一条，你会不断产出"只改了时间戳的伪修订"。

- **预算式门禁**：给"允许的不足"设配额，而不是要求 100% 完整。案例配额是全篇 2 处、关键模块 0 处。没有配额，稿子会永远卡死。

### 5.4 构建必须可重入

- 每次在临时目录（`data/.staging/<时间戳>_<选题>/`）构建。

- 门禁全过 → 原子平移到成品目录 `data/articles/<时间戳>_<选题>/`。

- 任何失败 → 直接删临时目录。

这样中断永远不会污染成品区，也不会出现"半成品被当成已完成"。

***

## 第 6 步：把固定动作拆成脚本

这是让流水线"稳定产出"的关键一步。**不脚本化的后果不是慢，是不一致**：同一件事这次做得好、下次漏一步，质量就会随状态波动。

### 6.1 先列一张"重复动作清单"

把每篇都要手动重复做的事写下来，按频率排序。判据是两条，都满足就脚本化：

1. 每篇重复 ≥ 3 次；
2. 输入和输出都能明确命名（能写成"给什么、得什么"）。

### 6.2 案例怎么拆的：四个脚本入口

案例把全部重复动作收成了四条命令行入口，职责互不重叠：

| 脚本                             | 负责什么                           | 输入               | 输出                                                            | 稳定性设计                              |
| ------------------------------ | ------------------------------ | ---------------- | ------------------------------------------------------------- | ---------------------------------- |
| `production.py`                | 图片打包 → 渲染 → 跑五层门禁 → 归档 → 写质量报告 | 选题、正文路径、研究包目录、封面 | 成品目录（平台成品 + 预览稿 + images）、`data/reports/<时间戳>_<选题>.json`、状态字段 | 时间戳临时目录构建，成功才原子平移，失败自清理            |
| `confirm_upload.py`            | 只写草稿箱，不群发                      | 质量报告 JSON + 平台凭证 | 草稿 + 状态 `UPLOADED`                                            | 必须显式带 `--confirm-upload`，默认不执行，防误触 |
| `review_analytics.py`          | 复盘一条龙：解析 → 补全 → 校验 → 出报告       | 后台导出报表（或无参重跑）    | 台账更新 + 研报（人读 md + 机读 json）                                    | 导入前去重、占位符拦截、写库前备份旧台账               |
| `build_cumulative_channels.py` | 汇总渠道累计表                        | 台账               | 渠道累计表                                                         | 人工覆盖表纠正误分组，防止重跑回退                  |

**照此做的建议**：先按"读、产、写"三类划边界——**检查类只读、构建类只产、写入类才碰外部系统**。三类混在一个脚本里，你就没法保证"重跑安全"。

### 6.3 拆一个动作的四步法

拿"把正文渲染成平台成品"这个动作示范：

1. **先定契约**：写清楚输入是什么、输出落到哪个路径、失败返回什么状态。契约先于实现。
2. **抽掉判断**：脚本只做机械动作。哪张图合格、哪个数字能用，这些判断不放进脚本，放进台账和配置。
3. **保证可重入**：临时目录 + 时间戳命名 + 成功才原子平移 + 失败即删。
4. **留证**：输出文件的哈希、命令、退出码、执行时间。没有留证，你就无法证明"这一步真的跑过"。

### 6.4 脚本上线前回答四问

| 问题           | 不合格的表现            | 合格的做法             |
| ------------ | ----------------- | ----------------- |
| 连跑两次结果一样吗？   | 第二次把第一次的输出覆盖成半成品  | 输出带时间戳目录，或明确幂等键   |
| 中途失败会留下半成品吗？ | 成品目录里出现缺图的残稿      | 临时目录构建，成功才平移      |
| 出错能定位到哪一步吗？  | 只打印一行异常           | 每步有独立错误码或退出码      |
| 输入缺失时怎么办？    | 静默跳过，产出"看起来正常"的空稿 | 明确报错，直接 fail-fast |

### 6.5 什么动作先别脚本化

- **一次性动作**（比如首次上传封面）：手做一次更快，做成脚本反而是负担。

- **判断还没稳定的动作**（比如"这段该详写还是略写"）：先把它写成规范条文，稳定后再考虑脚本化。

- **规则还在反复改的动作**：先把规则固化进画像卡或规范文件，再谈脚本。

**上线顺序建议**：先做只读检查类（门禁、审计），再做产出类（渲染、打包），最后做写入类（上传）。写入类风险最高，放在你已经有稳定门禁之后。

### 6.6 案例的一条硬经验

案例要求所有"取证类"执行都必须留"命令 + 退出码 + 输出文件 + 哈希"，只写一个 `status: executed` 会被门禁判为未执行。**同样的要求应当扩展到你的每一个脚本**：没有证据的"已完成"等同于没做。

## 第 7 步：定 skill 调度规则

skill 是能力外挂，用来补你缺的工具或数据源，**不能替代流程本身**。用错地方的 skill 比不用更糟：它会让你以为有证据，其实只是搜到了一篇二手文章。

### 7.1 怎么找、怎么选（顺序固定）

调度表不是拍脑袋填出来的。按这五步走，顺序不能换：

1. **先说规则**：向参与的人说明这一步要产出什么、什么算通过，再开始找。规则没说清就去搜 skill，搜回来的东西一定对不上门。
2. **先收倾向**：项目方向确认之后，先问对方有没有本项目倾向用的 skill（名称或能力描述都算）。有倾向的先纳入候选；判定不适用要写明理由，不能悄悄丢掉。
3. **再检索补齐**：拿已确认的项目方向，逐阶段检索能适配的 skill。检索是用来补齐盲区的，不是用来覆盖对方的倾向。
4. **给建议并说明理由**：把候选列成清单，每条写清：推荐 / 不推荐、放在第几步、产出什么证据、什么时候不该用、是否只是兜底。只报名字不给理由，等于把判断原样推回去。
5. **确认后才落表**：逐条确认后，才写进调度表。清单列出来不算完成，对方点头才算。

### 7.2 四条调度原则

1. **固定在阶段**：每个 skill 只在其负责的阶段被调用，不能当默认入口随手乱用。
2. **必须留痕**：调用要记录命令、退出码、输出文件、哈希。留不了痕的能力不要纳入流水线。
3. **只供原料，不做判断**：skill 产出的是数据与线索，进正文前必须过事实台账。
4. **兜底型排最后**：浏览器类能力只在前置工具拿不到关键证据时启用。

### 7.3 案例的调度表（照此填你自己的）

| 阶段            | 用哪个能力                                      | 解决什么                     | 必须留下的证据                      | 什么时候不用                              |
| ------------- | ------------------------------------------ | ------------------------ | ---------------------------- | ----------------------------------- |
| 第 2 步 取证      | 产业地图/选题类 skill（案例：a-share-industry-picker） | 先建立产业环节与代表主体的骨架          | 命令 + 退出码 + 输出文件 + 哈希         | 题材不是上市公司驱动时，标 `not_applicable` 并写理由 |
| 第 2 步 取证      | 行情/财务数据 skill（案例：akshare-stock）            | 拉取价格、财务指标的原始数值           | 同上                           | 标的不在覆盖范围时标不适用                       |
| 第 2 步 取证      | 个股分析 skill（案例：a-stock-analysis）            | 单公司经营数据交叉验证              | 同上                           | 同上                                  |
| 第 2 步 取证      | 自建抓取脚本                                     | 存档公开来源、生成清单与候选数字         | 快照 + sha256 + 来源清单           | 永远都要用（这是底座）                         |
| 第 2 步 取证（仅兜底） | 浏览器类 skill（案例：ego-browser）                 | 前置手段拿不到关键证据时，读取动态页或被拦截页  | 真实 URL、标题、发布日期、统计期、提取字段、采集时间 | **默认不启用**；能从前四项拿到就不用                |
| 第 3—6 步       | 不需要 skill                                  | 写作、制图、门禁、构建由脚本与你完成       | —                            | —                                   |
| 第 9 步 复盘      | 复盘工作流 skill（案例：wechat-post-publish-review） | 报表解析 → 字段补全 → 口径校验 → 出研报 | 研报 md + json、台账变更记录          | 数据还没导出时不用，不要用估算替他                   |

### 7.4 为什么顺序必须固定

案例把取证顺序写死为：**产业地图 → 行情/财务 → 个股分析 → 常规公开资料 → 浏览器兜底**。

原因不是偏好，而是**证据强度递减**：越靠前的来源结构化程度越高、可复核性越强；越靠后越接近"我看到了一个页面"。顺序一旦打乱，最常见的后果就是"先搜到一篇二手解读，就把它当成了源头"。

**照此做的规则**：把顺序写进规范文件，并且规定"前一档没跑完，不许跳到后一档"；唯一例外是前一档明确标 `not_applicable`。

### 7.5 不适用也要写清楚

不是每个题材都能用上每个 skill。不能用时不要硬用，但必须写明不适用理由——否则门禁无法区分"没做"和"不需要做"。

### 7.6 什么时候不该用 skill

- 规则还在探索期，产出无法稳定复现；

- 调用结果无法留痕（那它就进不了证据链）；

- 想用它直接生成正文——起草可以，但任何事实必须回台账核验；

- 拿它替代你该做的判断，比如"让 skill 决定这篇该写什么结论"。

### 7.7 复盘 skill 的边界

复盘 skill 只产出诊断与建议，**不自动改选题档位、不自动改门禁规则**。改哪一条、改到什么阈值，仍然是你拍板。这不是能力不足，是刻意设计：规则一旦能被脚本自己改，质量体系就失去锚点。

## 第 8 步：接交付

按第 0 步定的等级接：

**L1 可编程草稿**

1. 生成平台成品 + 本地预览稿（预览稿要能在浏览器里按手机宽度看）。
2. 你打开预览，逐屏（或逐卡）检查。
3. 你明确确认后，脚本才写入草稿箱。
4. 你在后台点发布。

**L2 仅人工粘贴**：跳过接口，产出"粘贴友好成品"，并附一份粘贴后检查清单（图片是否显示、编号是否错行、标题样式是否被平台改写）。

**L3 纯手工**：产出成品 + 操作清单，清单细到"哪张图放哪个位置"。

三档共同的检查点：写入前必须有人确认；写入后状态置为 `UPLOADED`；**绝不自动群发**。

## 第 9 步：接复盘

### 9.1 台账字段分三级

- **核心必填**（缺了报错）：发布日期、标题、阅读数（或该平台核心指标）。

- **建议可填**（缺了不阻断）：选题标识、载体类型、快照时点、曝光量、链接。

- **渠道可选**：平台后台能拆出的渠道字段。

缺失字段一律标"资料不足"，**禁止用其他数字反推**（比如用阅读数倒推曝光）。

### 9.2 三条口径红线

1. 快照时点固定，且只在**同一时点**的记录之间比较。
2. 以"标题 + 时点 + 平台"为唯一键，避免重复计数。
3. 录入前拦截占位符：出现"示例、待填、测试"直接拒绝入库。

### 9.3 规则四路落盘

复盘结论必须落成四类可执行物，缺一类就算复盘没做完：

| 落点     | 写什么            | 什么时候生效        |
| ------ | -------------- | ------------- |
| 策略池文件  | 选题档位（加码/维持/隔离） | 下次定题前必读       |
| 写作规范文件 | 结构、字段、表述、收尾样式  | 下次成稿前必读       |
| 教训文件   | 门禁失效案例、修订方向    | 下次门禁迭代的输入     |
| 门禁代码   | 可判定的新规则        | **下次跑门禁自动执行** |

### 9.4 什么才升格为规则

- 同类问题 ≥ 2 次且可判定 → 写成门禁代码（优先级最高）

- 出现 1 次或判不了 → 记教训文件观察

- 结构性的偏好 → 写进写作规范

- 平台适配经验（编辑器会破坏什么）→ 直接写成门禁，因为必然复发

## 第 10 步：把流水线跑起来

### 10.1 定一个负责人

| 角色     | 谁            | 负责什么                |
| ------ | ------------ | ------------------- |
| 责任主体   | 你，只有你        | 定题、事实把关、预览确认、发布、改规则 |
| 执行体    | 工作会话 / agent | 起草、按错误码修订、调度 skill  |
| 确定性执行器 | 你的脚本         | 构建、门禁、写入、复盘         |

任何状态跃迁只有一个决策人。两个人同时能拍板，出事就查不清谁批的。

### 10.2 目录隔离三条硬要求

1. 一任务一目录，目录名带时间戳。
2. 临时目录构建，成功才平移成品，失败即删。
3. 成品目录只读留证，修订产生新目录，不覆盖旧目录。

### 10.3 什么时候能并行

唯一判据：**是否存在共享可写产物**。

- 同一选题内：严格串行（段与段硬依赖）。

- 不同选题：可并行（目录天然隔离）。

- **一稿多平台**：属于"一稿多产物"，每个平台按各自画像卡**分别跑门禁**，结论不互认；成品放各自目录，禁止互相覆盖。

- 共享写点（失败计数、台账）：没有文件锁时，靠"同一时刻只跑一个"的纪律保证。

### 10.4 失败怎么回退

**回退到产生缺陷的最早一步，不要回到起点。**

| 缺陷                  | 回到         | 怎么处理               |
| ------------------- | ---------- | ------------------ |
| 来源不足、口径缺失、关键模块没证据   | 第 2 步      | 只补映射与台账，已有快照不重抓    |
| 单元缺答、字段不全、表述越界、差异不足 | 第 3 步      | 改正文，重跑门禁           |
| 越界、压字、比例超限、托管方式不对   | 第 4 步      | 改单图，重跑门禁           |
| 预览观感不好              | 第 3 或第 4 步 | 你指问题，改完重跑          |
| 平台写入失败（凭证、白名单、限流）   | 第 8 步      | 只重跑写入，不重跑门禁        |
| 已发布后发现问题            | 不回滚        | 作为复盘输入沉淀规则，是否补救你决定 |

**产物三分**：可复用（快照、哈希、已核验台账、已过门禁成品）永不重做；可修补（正文、单图、映射）原位改；必须废弃（临时构建目录）失败即删。

### 10.5 防死循环

同一稿件键（建议 `选题::稿件路径`）计数，成功清零；连续 3 轮失败即停，转人工三选一：**补资料 / 缩小选题 / 放弃**。你改变规则或补资料后，保留原记录，以新批次重新计数。

**一条铁律**：修补只改产物，不改门禁。门禁判错了，走"改规则"流程，不要在回退时临时放宽门槛——放宽一次，门禁就开始失效。

***

## 第 11 步：上线自检清单

首次跑通前，逐项确认：

**自动化能过的**

- [ ] 研究包门禁：来源数量、工具证据（命令 + 退出码 + 文件 + 哈希）、模块覆盖、时效

- [ ] 结构门禁：单元顺序、必备字段、每单元数值或书面边界、首屏图位置、图片不重复

- [ ] 呈现门禁：比例、越界、超框、压字、字号、托管方式

- [ ] 合规门禁：禁词、承诺性表述、资质敏感项

- [ ] 差异门禁：与上一版不同

- [ ] 构建可重入：临时目录 + 原子平移 + 失败清理

- [ ] **每个脚本都通过"四问"：幂等、原子、可定位、fail-fast**

- [ ] **每个 skill 调用都留了四件证据，不适用的写了理由**

**只能你目检的**

- [ ] 预览逐屏（或逐卡）读完，无文字遮挡、无裁切

- [ ] 手机宽度下字号可读

- [ ] 图文节奏：每张图是否紧邻它回答的问题

- [ ] 事实与台账一致，没有张冠李戴的口径

- [ ] 记录"已逐张目检 + 张数"

**交付前**

- [ ] 你已明确确认（不是"应该没问题"）

- [ ] 程序终点是草稿/粘贴成品，不是发布

- [ ] 台账已建，快照时点已写进日历

## 第 12 步：首篇试跑路径

不要一上来就把 12 步全自动化。按这个顺序跑通第一篇：

1. **手写一篇**：只用第 2 步研究包 + 第 3 步契约，手动检查。目的是验证契约够不够用。
2. **接证据门禁与结构门禁**：这两层平台无关，能立刻复用。跑三篇，修规则。
3. **接呈现门禁**：先只查越界与比例，跑通后再补压字、字号。
4. **抽脚本**：把已经跑顺手的三四个动作按第 6 步固化成脚本，先用只读类，再用产出类。
5. **接 skill**：只在取证阶段接，按固定顺序，先跑通一个再上一个。
6. **接交付**：先 L2（人工粘贴）验证成品质量，再考虑升级 L1。
7. **接复盘**：等累计 5 篇同快照时点数据后再做分组对比；样本不足时只做单篇诊断。

## 附录 A：搭建时会踩的坑

1. **把平台规则写死进代码**：换平台就得改源码。正确做法是从画像卡读配置。
2. **候选数字直接当事实**：抓取脚本识别到的数字必须先进候选池，人工核验才进台账。
3. **门禁只查标题不查内容**：章节齐了但没回答问题是常见误通过。
4. **用形容词做放行标准**：一旦出现"内容充分则可放行"，门禁就形同虚设。
5. **只靠几何检查代替目检**：脚本全过但图上文字被色条压住，案例真实发生过。
6. **没有反退化门禁**：会批量产出"只改时间戳"的伪修订。
7. **没有配额**：要求每章都完整，稿子永远卡在 `REVISION_REQUIRED`。
8. **复盘用估算数据**：一旦允许估算，后续策略判断都建立在假数据上。
9. **两个负责人**：状态跃迁责任不清，发布事故无法追溯。
10. **回退时放宽门禁**：这是门禁失效最快的方式。
11. **脚本兼职太多**：一个脚本同时做检查、构建、上传，重跑必然出错。
12. **只用 skill 不留痕**：只写"已完成"，事后无法证明跑过，等于没跑。
13. **把 skill 当默认搜索入口**：跳过结构化数据源，直接拿二手页面当证据。
14. **让 skill 决定结论**：skill 只供原料，结论必须由你基于台账给出。

## 附录 C：尚待你自行验证的点

案例只在一个平台上验证过，下面这些需要你实测后再定：

1. 你平台的数据成熟时点到底是几小时（不要照抄 72）。
2. 图片托管方式：内联、外链还是素材上传，哪种在你的平台不会失效。
3. 比例与字号下限：案例里的区间是项目经验值，不是平台硬限，必须用真机验证。
4. 粘贴后平台会改写什么（标题样式、编号、图片宽度），逐项实测后写进画像卡 `render_redlines`。
5. 平台发布能力等级：先按 L2 假设，确认有草稿接口后再升级 L1。
6. 取证阶段哪些 skill 在你的题材上真的可用——先跑一个标的不适用的，确认"不适用也能留证"这条路径是通的。
